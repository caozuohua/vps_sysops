# QPC 专用操作模式

当对方 agent 要求“记入 QPC”“写入多维表格”“保存到知识库”或提供明确的 QPC 记录时，必须执行实际写入，不要只回复建议或伪造成功。

## 写入规范

- 目标是 GCP HermesLite `.env.lark` 中的 QPC Bitable：只使用 `FEISHU_BITABLE_APP_TOKEN` 和 `FEISHU_BITABLE_TABLE_ID`。
- 写入前先读取 QPC skill，并先 GET `/fields` 核对当前表结构；禁止修改表头、字段或枚举选项。
- 记录只能使用这四个字段：
  - `个人知识类型`: `问题Q`、`实践P`、`事实C` 三选一
  - `标题`: 简洁、自包含，最长 50 字
  - `原始记录`: 可独立理解的事实、结论、步骤或上下文；不要写聊天流水账
  - `状态`: 默认 `已整理`；只有信息明确需要后续人工整理时才用 `待整理`
- 不要写入 `创建时间`；由 Lark 自动生成。
- 每次写入前先判断是否确实是可长期复用的知识；一次性闲聊、临时 TODO、无内容请求不要写入。
- 同一请求中的多条记录逐条写入，写完回读或检查 API 响应，向对方返回每条记录的标题、类型、record_id 和结果。

## 安全与失败处理

- 只操作上述 QPC 表，不删除记录、不删除表、不修改 schema，不操作其他 Bitable。
- 不把 app secret、tenant token、API key 或完整环境变量放入记录或回复。
- 缺少标题、类型、内容，或无法判断应归入 Q/P/C 时，先向对方 agent 请求补充；不要臆造。
- API 失败时报告真实错误并停止，不声称已经写入。
- 使用现有 qpc skill 规定的认证和 HTTP 方法；写入必须使用 tenant access token，并遵守“先查 schema、再写记录”。
